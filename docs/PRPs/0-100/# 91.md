> ### Phase 1: Decoder Seek & Pipe Flush (Backend)
> 
> 
> **CONTEXT:** The "starting mid-file" bug happens because the Decoder FFmpeg is either not resetting its internal timestamp or the Node.js pipes are still full of the previous track's PCM data.
> **TASK:** Modify `ObrHandler.ts`:
> 1. **Force Seek to Zero:** In the Decoder FFmpeg command, explicitly add `-ss 0` *before* the `-i` flag. This forces the demuxer to reset to the absolute start of the file.
> 2. **Pipe Isolation:** Ensure that for every new request, a fresh set of `PassThrough` streams (if used) is instantiated. Never reuse a pipe handle between two different `/obr-stream` requests.
> 3. **Unpipe on Close:** In the `req.on('close')` handler, explicitly call `decoder.stdout.unpipe()` and `obr.stdout.unpipe()` before killing the processes. This prevents data from "leaking" into the response object during the teardown.
> 
>

> * **Verification:** Use a simple Buffer comparison or check the WebM timestamps (if possible) to ensure the second file doesn't contain a single frame of the first file.

> ### Phase 2: MediaElement Source Purge (Frontend)
> 
> 
> **CONTEXT:** If the browser thinks it's still playing the old stream, it may try to "resume" at the last known timestamp (e.g., 00:45) even if the source URL changed.
> **TASK:** Modify `src/contexts/PlaybackContext.tsx`:
> 1. When switching tracks, call `audio.pause()`.
> 2. **Crucial:** Set `audio.currentTime = 0` BEFORE changing the `src` attribute.
> 3. After setting the new URL, call `audio.load()` to force the browser to re-initialize the demuxer for the new WebM stream.
> 4. Use the `play()` promise: `audio.play().catch(e => console.warn("Playback prevented:", e))`.
