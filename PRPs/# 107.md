# Product Requirements Prompt (PRP)

## 1. Project Context & Objectives
**Project:** AmbiToolbox
**Current State:** Toggling the Headphone (Binaural Preview) button during active playback halts the audio stream instead of seamlessly switching formats and resuming.
**Objective:** Refactor the `toggleHeadphones` handler to behave as an active "Stream Rebuild" event. It must capture the exact `currentTime`, preserve the user's playback intent, and invoke the `LOCKED_REBUILDING` state to ensure a smooth transition between binaural and stereo downmix streams.

## 2. Technical Decisions & Dependencies
* **Root Cause:** The current `toggleHeadphones` function only flips a boolean. This triggers the Step 3 Commit hook, but fails to update `requestedSeekTime` (causing a loss of position) and lacks a `playbackIntentRef = true` assertion (causing playback to stall).
* **Architecture Fix:** We will rewrite `toggleHeadphones` in `PlaybackContext.tsx` to mirror the logic of `commitSeek`. It must dynamically capture `state.currentTime`, apply the `enterRebuildLock`, arm the `playbackIntentRef`, and inject a fresh `seekNonce` to guarantee execution.

## 3. Implementation Phases

### Phase 1: Logic Replacement
* **Objective:** Replace the passive toggle with an active, state-aware pipeline rebuild.
* **Instructions:**
    1. Open `src/contexts/PlaybackContext.tsx`.
    2. Locate the existing `toggleHeadphones` function.
    3. Replace it entirely with the following deterministic logic:

    ```typescript
    const toggleHeadphones = () => {
        if (state.isRebuilding) return; // Prevent spamming the pipeline

        const audio = audioRef.current;
        if (!audio) return;

        const wasPlaying = !audio.paused;
        const currentPlayhead = state.currentTime;

        // If it was playing, we must ensure it auto-resumes after the new stream loads
        if (wasPlaying) {
            playbackIntentRef.current = true;
            audio.pause();
        }

        // Engage the UI lock and failsafe timer
        enterRebuildLock(wasPlaying);

        // Force Step 3 Commit with the current playhead position and a fresh nonce
        setState(prev => ({
            ...prev,
            isHeadphonesOn: !prev.isHeadphonesOn,
            requestedSeekTime: currentPlayhead,
            seekNonce: Date.now() 
        }));
    };
    ```
* **TDD Checkpoint:** AGENT INSTRUCTION: Start the development server. Load a multichannel audio file and initiate playback. While the file is actively playing, click the Headphones toggle in the Transport UI. Verify that the UI enters the `BUFFERING` state momentarily, the audio resumes from the exact position it was toggled at, and playback continues seamlessly. Do not proceed to Phase 2 until this manual/visual assertion passes.

### Phase 2: Peer Function Audit (HRTF Profile)
* **Objective:** Ensure changing the HRTF profile dynamically also triggers a seamless rebuild.
* **Instructions:**
    1. The `setHrtfProfile` function currently suffers from the exact same architectural flaw as the old headphone toggle. 
    2. Locate `setHrtfProfile` in `PlaybackContext.tsx`.
    3. Rewrite it using the identical architectural pattern provided in Phase 1, passing the new `profile` string to the state update instead of flipping the boolean.
* **TDD Checkpoint:** AGENT INSTRUCTION: Open the Settings Modal via the transport cog wheel while audio is playing. Change the HRTF profile from Neumann to Kemar. Assert that the audio buffers and resumes exactly as it did for the headphones toggle.

## 4. Final Review
Verify that the Transport UI's `BUFFERING` indicator accurately reflects the backend pipeline rebuild time during format swaps. Ensure that toggling these settings while the audio is *paused* updates the backend stream without accidentally starting playback.
