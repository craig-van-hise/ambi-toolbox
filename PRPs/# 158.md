# Product Requirements Prompt (PRP) — 🔵 Active (Waiting for Human Validation)

## 1. Project Context & Objectives
**Context:** AmbiToolbox is an Electron-based spatial audio suite utilizing a 4-stage pipeline (`Decoder -> Rotator -> OBR -> Encoder`) for real-time monitoring. 
**Issue:** The user reports a critical transport failure: "After I play something then stop it doesn't play any more." Log analysis shows the pipeline processes a file successfully to EOF and triggers `Killing all processes and cleaning up pipes...`. However, subsequent playback attempts fail, indicating either the backend is failing to spin up a new pipeline for the same file, or the frontend `TransportContext`/`HTMLAudioElement` is retaining a dead stream state.
**Objective:** Hard-reset the frontend audio element state upon stop/EOF and implement deterministic cache-busting on the stream URL to force the backend to instantiate a fresh pipeline on replay.

## 2. Technical Decisions & Dependencies
To definitively resolve this transport lock-up without cognitive load on the worker agent, implement the following architectural mandates:
1.  **Frontend State Annihilation:** When `Stop` is triggered (or EOF is reached), the `HTMLAudioElement.src` must be explicitly nullified (e.g., `audio.src = ''`), followed by an `audio.load()` call to purge the browser's media buffer. 
2.  **URL Cache-Busting:** The `AudioEngineContext` must generate a fresh stream URL using a new temporal query parameter (`&_t=Date.now()`) *every single time* the Play command is issued from a stopped state. This circumvents aggressive browser caching and forces the `StreamServer` to view it as a novel request.
3.  **Backend Pipeline Reaping:** In `ObrHandler.ts` and `StreamServer.ts`, ensure that upon triggering `Killing all processes...`, the internal reference map tracking active pipelines for the client is `deleted` and garbage collected. A new request must not encounter a "zombie" pipeline object.
