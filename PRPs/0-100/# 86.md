
### Product Requirements Prompt (PRP): Pipeline Bug Fixes (Phased TDD)

> **OBJECTIVE:** Fix three critical bugs in the streaming pipeline: an HTTP header crash, hardcoded channel parameters in React, and a complete architectural bypass of the C++ OBR sidecar in `ObrHandler.ts`.
> **EXECUTION RULES:** > You must execute this task using strict Test-Driven Development (TDD) across three distinct phases. You MUST write and execute the specified test at the end of each phase. You are strictly forbidden from proceeding to the next phase until the current phase's test yields a passing result (green light).
> ---
> 
> 
> ### Phase 1: Fix the HTTP Header Crash (Backend)
> 
> 
> **CONTEXT:** When React mounts, it sends `file=null`. The backend correctly sends a 400 error but continues executing the function, trying to spawn FFmpeg into a closed response, causing an `ERR_HTTP_HEADERS_SENT` crash.
> **TASK:** In the `/obr-stream` route handler (`ObrHandler.ts` or equivalent), locate the error handler for missing files. Add a `return` statement immediately after `res.status(400).send(...)` to halt execution.
> **TEST:** Write and run `scripts/test-null-file.ts`. It must spin up the server, send a GET request to `/obr-stream?file=null`, and assert that the response is `400 Bad Request` AND that the Node server process remains stable without throwing an unhandled promise rejection.
> **CHECKPOINT:** Stop and evaluate. Do not proceed to Phase 2 until this test passes.

> ### Phase 2: Fix the React Frontend Parameters (Frontend)
> 
> 
> **CONTEXT:** `src/contexts/PlaybackContext.tsx` is currently hardcoding `channels=4` and failing to guard against `file=null` requests on mount.
> **TASK:** Modify `PlaybackContext.tsx`:
> 1. Add a guard: The HTML5 `Audio` element must not request the `/obr-stream` endpoint if the `file` state is null or undefined.
> 2. Read the actual channel count from the loaded audio file's metadata (which `WavDecoder` is already parsing) and inject that dynamic value into the `/obr-stream` URL instead of hardcoding `4`.
> **TEST:** Write a lightweight test script (`scripts/test-url-builder.ts`) that imports the URL construction logic used in `PlaybackContext.tsx`. Pass it a mock state object representing your 16-channel Clock Test WAV. Assert that the generated URL string correctly contains `channels=16`.
> **CHECKPOINT:** Stop and evaluate. Do not proceed to Phase 3 until this test passes.

> ### Phase 3: Rebuild the True 3-Stage Pipeline (Backend)
> 
> 
> **CONTEXT:** `ObrHandler.ts` is currently bypassing the C++ sidecar entirely, running a single FFmpeg process that blindly downmixes 16 channels to stereo, creating spatial aliasing ("pretzel space").
> **TASK:** Gut the current stream logic in `ObrHandler.ts`. You must implement the true 3-stage Sidecar pattern that was previously verified:
> 1. **Decode:** FFmpeg reads the file and outputs raw 32-bit float PCM (`f32le`) to `stdout`. Pass the exact channel count derived from the query parameters.
> 2. **Process:** The `obr_stream` C++ executable reads `stdin` (raw PCM), processes the binaural math, and outputs stereo `f32le` PCM to `stdout`.
> 3. **Encode:** A second FFmpeg instance reads the stereo PCM from `stdin` and encodes it to `webm/opus` to the Node `res` object (`pipe:1`).
> *Ensure all pipes are secure and all child processes are gracefully killed on disconnect.*
> **TEST:** Write and run `scripts/test-3-stage-pipeline.ts`. It must request a valid multi-channel file through the endpoint and verify two things: 1) The output is a valid WebM stream, and 2) The `obr_stream` executable was actually spawned and active during the request.
> **CHECKPOINT:** Report back to the user ONLY when Phase 3 is complete and all tests are green.
