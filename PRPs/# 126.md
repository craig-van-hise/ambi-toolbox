### PRP #126: Stereo2Ambix FDN Parameter Plumbing and Routing Diagnostics

**Objective:**
Trace the FDN control parameter from the Frontend UI down to the Python DSP script to identify where the variable is being dropped, ignored, or hardcoded, resulting in a disconnected FDN stage.

**Context & Constraints:**

* **Target Files:** `src/components/ToolViews.tsx` (or relevant UI file), `electron/handlers/Stereo2Ambix.ts`, and `py/stereo_to_ambix.py`.
* **Current State:** Adjusting the FDN parameter (0 to 100) has zero effect on the audio. The output is identical regardless of the setting.
* **Directives:** Do not modify the core DSP math. Focus strictly on full-stack parameter passing, IPC bridges, and Python `argparse` implementations.

**Execution Tasks:**

#### Task 1: UI to IPC Hand-off Verification (Frontend)
status: ✅ Completed

1. **Inspect the UI Component:** Locate the FDN slider/input in the React frontend. Verify that the `onChange` event is correctly updating the component state.
2. **Verify the IPC Call:** Check the `window.electronAPI` (or equivalent) call that dispatches the `Stereo2Ambix` job. Ensure the FDN value is actually included in the payload object being sent to the Electron Main process.

#### Task 2: Handler to Python CLI Argument Verification (Electron Backend)
status: ✅ Completed

1. **Inspect the Handler:** Open `electron/handlers/Stereo2Ambix.ts`.
2. **Trace the Payload:** Verify that the handler successfully extracts the FDN value from the incoming IPC request.
3. **Check the Spawn Command:** Look at the `spawn` or `exec` command that calls `py/stereo_to_ambix.py`. Is the FDN value being passed as a command-line argument (e.g., `--fdn-amount ${fdnValue}`)? If it is missing from the arguments array, add it.

#### Task 3: Python Argparse and Integration Check (DSP Script)
status: ✅ Completed

1. **Inspect Argument Parsing:** Open `py/stereo_to_ambix.py`. Check the `argparse` setup. Is it configured to accept the `--fdn-amount` (or equivalent) argument?
2. **Trace the Variable:** Follow the parsed argument down to the DSP function call. Is the parsed value actually being passed into the `apply_fdn()` or `upmix()` function, or is the function currently using a hardcoded default value (e.g., `fdn_gain = 0.5`) left over from early prototyping?

#### Task 4: The "Alive" Sanity Test (Python Override)
status: ✅ Completed

1. **Temporary Hardcode:** If Tasks 1-3 show the parameter is flowing correctly, temporarily hardcode an extreme FDN value *inside* the Python DSP loop (e.g., set the FDN mix to 100% and decay to 10 seconds).
2. **Execute:** Run a test file.
3. **Evaluate:** If the output is *still* unchanged and unresponsive to the hardcoded extreme value, the FDN DSP block itself is bypassed or overwritten downstream before the file is written.
