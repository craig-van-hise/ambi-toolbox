
### Product Requirements Prompt (PRP): Linear State Machine & Loop Guard (Phased TDD)



> **CRITICAL REFACTOR: RACE CONDITION & INFINITE LOOP FIX**
> The previous implementation created a severe race condition. You attempted to synchronously trigger `.play()` with an incomplete URL (missing `channels`) *before* the `WavDecoder` finished probing. When the probe finished, it overwrote `audio.src`, aborting the play request and throwing the React UI into an infinite Play/Pause render loop.
> **EXECUTION RULES:**
> Use strict TDD. You must completely decouple the "Intent to Play" from the "Probe", and guard against React state loops.
> ---
> 
> 
> ### Phase 1: The Linear Pipeline (Frontend)
> 
> 
> **TASK:** Refactor the track switching logic in `src/contexts/PlaybackContext.tsx` into a strict 3-step linear flow:
> 1. **Step 1: The Intent (User Click):** When a file is double-clicked in the queue, do exactly three things synchronously:
> * `audio.pause()`
> * `setPlaybackIntent(true)` (A ref or state storing the user's desire to play).
> * `setSelectedFile(file)` (This triggers Step 2).
> * *Crucial:* Clear any existing probe data so we don't accidentally reuse old channel counts.
> 
> 
> 2. **Step 2: The Probe:** A `useEffect` watches `selectedFile`. It runs `WavDecoder`. On success, it updates `setProbeData({ channels: ... })`. It does NOT touch the audio element.
> 3. **Step 3: The Commit:** A separate `useEffect` watches `probeData`. When `probeData` populates:
> * Construct the FULL `/obr-stream` URL (including `channels`).
> * `audio.src = url; audio.load();`
> * If `playbackIntent` is true, call `audio.play().catch(console.error)` and immediately set `playbackIntent` to false.
> 
> 
> 
> 
> **TEST:** Write a React unit test (`scripts/test-linear-pipeline.tsx`) mocking this exact 3-step state flow. Assert that `audio.src` is NEVER set until `probeData` exists, and `.play()` is only called on the complete URL.
> **CHECKPOINT:** Stop and evaluate. Do not proceed until this test is green.

> ### Phase 2: Infinite Loop Guard (Frontend)
> 
> 
> **CONTEXT:** The logs show `UI Play triggered` and `UI Pause triggered` firing dozens of times a second. React state is ping-ponging against the native `<audio>` events.
> **TASK:** Audit `PlaybackContext.tsx` and `Transport.tsx`:
> 1. **Guard UI Actions:** If the user clicks the UI "Play" button, only call `audio.play()` if `audio.paused === true`. If they click "Pause", only call `audio.pause()` if `!audio.paused`.
> 2. **Guard State Updates:** Inside the `<audio>` element's `onPlay` and `onPause` native event listeners, only update the React `isPlaying` state if it actually differs from the new native state. This breaks the infinite loop.
> 
> 
> **TEST:** Manually verify in the Dev Environment.
> * Double-click a track. It must probe, load, and play cleanly.
> * Console logs must show exactly ONE play execution, with no Play/Pause spam.
> 
>
