### Product Requirements Prompt (PRP): File Switch State Synchronization



> **OBJECTIVE:** Fix the "stuck at zero" malfunction when double-clicking a new track. The player must automatically and cleanly begin playback when a new file is loaded, without requiring the user to manually stop and start the transport.
> **EXECUTION RULES:** > Use strict TDD across two phases. You must not proceed to Phase 2 until Phase 1 passes.
> ---
> 
> 
> ### Phase 1: Isolate File Load vs. Seek Logic (Frontend)
> 
> 
> **CONTEXT:** The recent auto-resume logic for the timeline scrubber is interfering with loading brand new files. When a new file is loaded via the queue, the `<audio>` element is getting stuck in a paused state while the React UI state goes out of sync.
> **TASK:** Modify `src/contexts/PlaybackContext.tsx`:
> 1. **Distinct Code Paths:** Ensure there is a clear, separate function for `loadNewFile(filePath)` versus `handleSeek(timestamp)`.
> 2. **Reset State on Load:** When `loadNewFile` is triggered, immediately zero out the virtual playhead, reset the seek offset to 0, and explicitly set the React playback state to `isLoading` or `isBuffering`.
> 3. **The `canplay` Auto-Play:** For new files, do NOT blindly call `audio.play()` synchronously after setting `audio.src`. You must attach a one-time event listener to the `audio` element for the `canplay` (or `loadedmetadata`) event. Once that fires, execute `audio.play().catch(...)` to guarantee the browser actually starts the stream.
> 
> 
> **TEST:** Write a programmatic test (`scripts/test-file-switch-autoplay.ts`).
> * Mock the React context and the HTML5 `<audio>` element.
> * Simulate loading "Track A" and assert it reaches a playing state.
> * Trigger a new file load ("Track B").
> * Assert that `audio.currentTime` is reset to 0, `audio.src` is updated, and that `.play()` is successfully called ONLY AFTER the mock `canplay` event is emitted.
> **CHECKPOINT:** Stop and evaluate. Do not proceed until this state machine test is green.
> 
> 
> ---
> 
> 
> ### Phase 2: React UI State Synchronization (Frontend)
> 
> 
> **CONTEXT:** The Transport UI must accurately reflect what the `<audio>` element is actually doing to prevent the user from having to press "Stop/Play" to fix desyncs.
> **TASK:** Audit the event listeners in `PlaybackContext.tsx`:
> 1. Ensure the React state for `isPlaying` is strictly driven by the `<audio>` element's native `onPlay` and `onPause` events, NOT just the user's clicks on the UI buttons.
> 2. If the audio fails to auto-play on a new file load (e.g., due to browser autoplay policies), the native `onPause` or `onError` handler must catch this and update the UI to show the "Play" button, rather than getting stuck showing a "Pause" button while the track is silent at 0:00.
> 
> 
> **TEST:** Manually verify in the development environment.
> * Double-click Track A. It should play automatically.
> * While Track A is playing, double-click Track B. It should seamlessly stop Track A, reset the playhead to zero, and automatically begin playing Track B.
> 
> 
> **REPORTING:** Report back only when both the automated test passes and you have verified the UI state sync.
